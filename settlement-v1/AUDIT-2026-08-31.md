# settlement-v1 — pre-deploy adversarial audit (2026-08-31)

Auditor: internal (Syed's lane), performed before requesting deploy funds.
Method: full source read (670 lines), every finding verified by construction
of the failing input, fixes verified by functional tests against the real
runtime (`solana-program-test`, matching the pinned `solana-program` 2.3.0).
Scope: `settlement-v1/src/lib.rs` at the state deployed to `main`
(`cee1cb4`), plus the fixes in this change.

Context that shaped severity: the previous program
`5g9zWHF1Vv6GiGpA2ZbJQbSCDZd5hAk9AyvabRJvKFx2` was closed on 2026-08-29 by an
attacker holding the stolen deployer key. That attacker knows our addresses
and watches our on-chain activity. "Requires an attacker monitoring the
deploy" is therefore NOT a mitigating assumption for this deployment.

## H-1 — 1-lamport transfer bricks `initialize_config` permanently (FIXED)

`create_pda_account` refused to create the PDA if it held ANY lamports
(`pda.lamports() > 0 → ERR_ALREADY_INITIALIZED`). The config PDA address is
computable by anyone from the program id alone (constant seed). Between the
deploy finalizing and `initialize_config` landing, any third party could
transfer 1 lamport to that address; `initialize_config` would then fail
forever — no code path recovers, the program can never be configured, and the
full deploy rent is wasted. The same dusting blocked any chosen receipt PDA,
griefing individual `payment_id`s (ERR_REPLAY on a payment that never
happened).

**Fix:** initialization state is now defined by DATA and program ownership,
never by lamports. Only this program can PDA-sign an `allocate`, so data at
these addresses is provably ours; lamports are not. A dusted (system-owned,
zero-data) PDA is topped up to rent-exemption if short, then
`allocate` + `assign` executed under the PDA's signature — the same pattern
Anchor's `init` uses. Real replay (a written receipt) still rejects with
`ERR_REPLAY`; re-initialization still rejects with `ERR_ALREADY_INITIALIZED`.

**Proof:** functional tests `dusted_config_pda_does_not_brick_initialize`,
`dusted_receipt_pda_does_not_block_payment` (positive), and
`real_replay_is_still_rejected`, `initialize_twice_is_rejected` (negative —
asserting the exact error codes, not just failure).

## M-1 — `set_admin` is single-step (ACCEPTED, mitigated operationally)

A `set_admin` to a wrong or dead pubkey permanently loses pause/treasury
control (the upgrade authority can still replace the whole program, so it is
recoverable at the cost of an upgrade). Two-step handover (propose/accept)
would remove the risk but grows the state layout. Decision: keep single-step;
the only planned `set_admin` is the one-time move to the Squads multisig,
executed from the runbook with the address triple-checked against the Squads
UI. Revisit if admin ever needs to move again.

## L-1 — Token-2022 mints unsupported (BY DESIGN)

`pay_token` accepts only `spl_token::id()`. Mainnet USDC
(`EPjFW…Dt1v`) and USDT (`Es9vM…wNYB`) are classic SPL mints, so this
excludes nothing we support — but a future Token-2022 stablecoin would need
a program change. Documented, no action.

## L-2 — `ERR_REPLAY` previously conflated dusting with replay (FIXED with H-1)

An SDK retrying a payment whose PDA had been dusted would have reported
"replay" for a payment that never settled — a misdiagnosis with support
cost. After H-1's fix the code only says replay when a receipt was written.

## Informational

- `valid_until` has no upper bound; `i64::MAX` disables expiry. The quote
  TTL is the backend's responsibility (matches EVM v1.3 behavior).
- The merchant account is caller-supplied and unconstrained by the program.
  This is the v1.3 design: the RECEIPT binds payer/merchant/amounts on
  chain, and the off-chain verifier checks the receipt against the
  registry's expected merchant. The verifier MUST do so (as it does for
  EVM routes).
- Each payment creates a 170-byte receipt: rent ≈ 0.0020 SOL per payment,
  paid by the payer, permanently locked (no close path). Fine for
  supervised tests; for volume, a receipt-closing policy is a v1.4
  question.
- Payer paying themselves, or merchant == treasury, moves value consistently
  and records an honest receipt; no advantage to either.

## What was checked and found sound

- `initialize_config` gated on the program's real upgrade authority via
  `UpgradeableLoaderState` deserialization (program account identity,
  executability, loader ownership, programdata linkage all verified).
  Negative test: `non_upgrade_authority_cannot_initialize`.
- Deploys **paused** (fail closed); explicit unpause after inspection.
- Exact instruction-data lengths; checked arithmetic throughout; split
  conservation (`merchant + treasury == gross` by construction); AIFP-1
  rejects fee-rounds-to-zero (`gross < 100`).
- `pay_token`: token program pinned to SPL Token, mint pinned to config's
  USDC/USDT, payer/merchant/treasury token accounts checked for mint match,
  treasury token account checked for owner == config.treasury,
  `transfer_checked` with on-chain mint decimals (no decimal confusion).
- Receipt written before transfers; any transfer failure reverts the whole
  transaction (no receipt without settlement, no settlement without
  receipt).
- Config/receipt PDAs: only this program can place data at those addresses
  (allocate requires the PDA signature), so `Config::load`'s magic/version
  check cannot be spoofed by a third party.
- No `declare_id!` — program id comes from the runtime. The old audit's C-4
  (program id trusted from the wire) is an SDK-side fix; C-5
  (`b2b_pay_with_split` undeployed) is moot — no such instruction exists
  here.
